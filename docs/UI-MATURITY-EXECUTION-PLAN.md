## 1. 目标与使用方法

将 Mai 的界面整理为适合长期使用的 Windows 桌面伴侣：安静、清楚、有角色温度。聊天是最明确的主入口，复杂配置按需呈现，用户在正常、等待、失败与恢复状态下都知道下一步如何操作。

本计划依据用户确认的五个方向：信息层级、视觉规范、聊天体验、操作反馈、素材一致性。它用于分批开发与验收，不要求重写整个 UI，也不引入新的前端框架。

执行前完整阅读根目录 `AGENTS.md`、本计划、[当前设计系统](MAI-DESIGN-SYSTEM.md)及任务涉及的实际代码。先核对当前 Git 状态与本文件基线；后续代码如果已实现某项，补验收证据，不重复开发。每次只推进一个可独立验证的批次。

本次用户请求是编写执行计划；本文件本身不代表新增功能、真实服务调用、提交、推送或市场发布的授权。后续收到开发指令后，按约定范围执行日常实现和验证，无需逐项确认普通排版细节。

## 3. 设计规范与产品边界

### 3.1 页面层级

- 侧栏：身份区紧凑，主操作突出，生活与资料分组可发现；选中、展开、悬停状态各有含义，不把每个入口都做成主按钮。
- 聊天：以文字和阅读节奏为主，保留足够留白，不给普通回复增加装饰卡片；技术状态按需展开。
- 输入区：发送是主操作，一次性语音输入和语音通话分别标注；Workspace 授权仍保留明确入口。不得为简洁而删除能力或隐藏授权状态。
- 设置：按外观、陪伴偏好、语音、模型连接、数据与隐私、诊断与关于六类组织；标明必需、可选和高级内容，不一次展开全部技术细节。
- 角色：主要出现在头像、桌宠、衣橱和少量空状态。不能把低分辨率精灵图放大成高清主视觉。
- Work：可以共享颜色和控件规范，保留自己的项目、工作会话、审批与运行状态语义。

### 3.2 视觉尺度

以下为后续校准的起点。已落地数值以源码为准；修改时通过现有 token 或明确的页面规则表达，不新增平行主题系统。

| 项目 | 设计约定 |
| --- | --- |
| 正文 | 以 15px、约 1.85 行高为起点；结合中文长段落与现有字号偏好检查 |
| 层级 | 页面标题约 20–24px，操作文字约 14px，辅助说明约 12px；时间约 11px，只承载低优先级信息 |
| 间距 | 优先复用 4、8、12、16、20、24、32 的现有间距体系 |
| 形状 | 控件约 6–8px、分组约 11px、输入区与气泡约 14px；不同职责允许不同圆角 |
| 强调 | 浅色以 `#70578E`、深色以现有主题强调色为基线；避免紫色底、粗边框、阴影同时强调 |
| 阅读宽度 | 主阅读区域约 700px；长单词、路径、代码不能撑宽窗口 |
| 导航 | 常规侧栏 224px，小桌面 190px；不超过 780px 使用可展开导航 |
| 状态 | 每个交互控件检查默认、悬停、聚焦、按下、选中、禁用、忙碌；不得仅靠颜色区分错误 |
| 动效 | 沿用现有减少动画和关闭动画设置；历史批量加载不逐条入场，不新增无意义循环动画 |

文本对比度以普通正文 4.5:1、大字 3:1 为内部验收目标；关键控件边界与焦点指示以 3:1 为目标。要检查实际背景叠加后的结果，不以一对 token 的计算替代整页检查，也不据此宣称获得无障碍认证。

### 3.3 不可破坏的边界

1. Chat 继续走 `ChatService -> ChatRequestService -> ModelGateway -> Provider`。UI 工作不引入工具调用、自动行动或 Agent 循环。
2. Work 与 Chat 的会话、记忆和任务所有权保持独立。取消与终态沿用既有 Runtime，不在 Renderer 创建第二套权威状态。
3. 设置、密钥、文件访问和持久化继续归 Main；不扩大 Preload / IPC 接口，不从 Renderer 直接访问文件系统。
4. 保留现有设置项、所有用户数据、备份和本地资源。UI 草稿不自动写入 Chat、Memory 或日志。
5. 普通设置显式保存；外观在设置内预览，离开后恢复保存值；壁纸、头像、衣橱按独立操作生效。若拟改变该语义，应先明确产品决策。
6. 不重绘已恢复的三套 Q 版服装，不更改共同基础动作和专属动作；Live2D 制作继续冻结。
7. 不随公共源码或安装包增加用户壁纸、第三方头像、密钥或真实聊天记录。后续发布仍遵守 NSIS 与干净源码产物规则。

### 阶段 B：聊天、首次连接与操作反馈

目标：先完善日常主路径，再扩展周边页面。

| 场景 | 目标行为 | 验收重点 |
| --- | --- | --- |
| 未连接模型 | “连接模型”直达模型设置；说明本地存储与云端请求；仍可查看其他可用页面 | 不出现无意义发送失败；不泄露密钥 |
| 发送等待 / 流式回复 | 及时呈现进行中状态；停止入口明确；正文逐步出现 | 不创建重复请求，不跳动输入区 |
| 用户停止 | 显示取消中，等待既有运行时确认终态后恢复操作 | 不提前把取消显示为完成；取消失败有可理解反馈 |
| 网络、服务或配置错误 | 说明发生了什么和下一步；配置错误引导设置，其他错误保留可编辑文本 | 不自动重试，不覆盖后来输入的新草稿 |
| 已有部分回复后失败 | 明确本次未完整完成，显示内容及是否持久化须遵循 Main 返回的事实 | 不编造完整回复，不将失败响应伪装成成功记录 |
| 设置保存 | 保存中禁止重复提交；成功反馈；失败保留草稿并允许修正 | 用真实 Main 故障注入验证，不只检查模拟成功 |
| 空列表 | 告诉用户这里有什么，并提供一个已有且可用的下一步入口 | 没有假数据，不出现无法执行的按钮 |
| 诊断详情 | 用户文案与技术详情分开；沿用现有脱敏诊断入口 | 不向 UI 或导出新增正文、Key、堆栈等敏感数据 |

- [ ] 邀请未参与设计的用户执行上述主要任务，记录卡住的位置、误点和求助；至少完成一轮观察与修正，不以开发者熟悉入口代替可用性证据。

完成条件：P0/P1 问题关闭，P2 有明确处置记录；提供自动化、人工操作、真实服务、安装升级四类独立结论。用户视觉验收与市场发布决策另行记录，不由测试数量推断。

## 5. 验证方法与执行命令

文档编写不需要重跑业务测试；以下命令供后续修改相应代码时执行。先确认依赖可用。避免依赖仅在本地未提交 `package.json` 中存在的脚本，UI smoke 使用实际 Node 文件入口。

```powershell
# 在仓库根目录执行；仅改变当前 PowerShell 进程的环境。
# 将 APPDATA 指向独立目录，避免 UI smoke 读取正式资料的文件哈希。
$uiQaRoot = Join-Path $env:TEMP ('mai-ui-qa-' + [guid]::NewGuid().ToString('N'))
New-Item -ItemType Directory -Path $uiQaRoot | Out-Null
$uiSavedAppData = $env:APPDATA
$uiSavedElectronMode = $env:ELECTRON_RUN_AS_NODE
$uiSavedOutput = $env:MAI_UI_REDESIGN_OUTPUT
$uiSavedFailureMode = $env:MAI_UI_SAVE_ERROR_SMOKE
try {
  $env:APPDATA = $uiQaRoot
  $env:ELECTRON_RUN_AS_NODE = $null
  $env:MAI_UI_REDESIGN_OUTPUT = Join-Path $uiQaRoot 'screenshots'

  npm.cmd test
  if ($LASTEXITCODE -ne 0) { throw '业务测试失败' }
  node test/ui-redesign-smoke.js
  if ($LASTEXITCODE -ne 0) { throw 'Renderer smoke 失败' }

  $env:MAI_UI_SAVE_ERROR_SMOKE = '1'
  node test/packaged-ui-smoke-runner.js node_modules/electron/dist/electron.exe
  if ($LASTEXITCODE -ne 0) { throw 'Main/Preload smoke 失败' }
  $env:MAI_UI_SAVE_ERROR_SMOKE = $null
  node test/packaged-chat-close-smoke-runner.js node_modules/electron/dist/electron.exe
  if ($LASTEXITCODE -ne 0) { throw '窗口关闭 smoke 失败' }
} finally {
  $env:APPDATA = $uiSavedAppData
  $env:ELECTRON_RUN_AS_NODE = $uiSavedElectronMode
  $env:MAI_UI_REDESIGN_OUTPUT = $uiSavedOutput
  $env:MAI_UI_SAVE_ERROR_SMOKE = $uiSavedFailureMode
}
```

- 上述 `packaged-*` 命令传入本地 Electron，验证的是源码运行，不是安装包。
- 衣橱或播放器变更时，另运行 `node --test test/pet-wardrobe.test.js` 和 `node test/pet-wardrobe-smoke.js`，检查动态证据。
- 启动动画发生变更时，另运行 `node test/startup-animation-smoke.js`；本计划不要求更换已有动画。
- 测试失败先定位产品问题还是环境问题；修复后重跑受影响检查，保留失败原因。通过后不为增加测试次数重复执行。
- 原有 UI smoke 读真实 APPDATA 路径的行为尚在：未设置上述隔离环境时不能宣称“未接触正式数据”。真实 Main smoke 使用自己的临时 userData，仍需阅读脚本确认边界。
- 自动化应验证真实模块组合后的行为。对简单颜色、圆角修改以渲染截图和交互复核为主，不新增只匹配 CSS 文本的测试。

## 6. 每批交付与完成判据

每个批次记录以下内容，建议保存于 `artifacts/ui-maturity/<batch>/`；正式设计规范发生变化时同步 `docs/MAI-DESIGN-SYSTEM.md`，不把历史验收记录写进 `AGENTS.md`。

| 字段 | 必填内容 |
| --- | --- |
| 范围 | 批次、基线 SHA、受影响页面、修改文件、保留的无关工作 |
| 问题与结果 | 具体触发步骤、修改前后行为、对应任务编号 |
| 验证 | 实际命令、退出结果、测试资料是否隔离、截图所在位置 |
| 人工证据 | 实际执行的操作、主题、窗口内容尺寸、Windows DPI；未操作则写“未验证” |
| 未完成项 | 已知问题、原因、下一步；不得用“基本完成”隐藏阻断 |
| 版本状态 | 是否提交/推送/打包，以及对应 SHA；没有执行的动作不填写成功 |

提交遵循 Conventional Commits。仅暂存本批次相关内容，核对暂存差异；混有其他未提交工作时，应验证实际提交版本而不是直接借用整个工作区的测试结果。推送后核对远程 SHA。发布产物只在明确发布范围内生成。

## 7. 下一次开发的具体起点

下一批从阶段 A 与阶段 B 的状态盘点开始，不重新制作已接受的聊天/设置静态稿：

1. 阅读并核对基线，复现连接未配置、发送中、停止、请求失败、保存失败五个场景。
2. 为每个场景写出当前提示、可操作按钮、是否保留输入、是否改变持久化状态及证据。
3. 优先修复已复现的状态误导或恢复路径缺口，再统一文案和视觉反馈。
4. 扩充有实际价值的状态回归，交付新截图、测试结果和剩余问题；然后推进阶段 C、D。

最终期望是用户能顺利完成日常任务、理解运行与保存状态，并在失败后恢复使用。外观截图、自动化测试和真实使用验收各提供一部分证据，三者不能互相替代。
